= Quarkus - Open API Generator - Moqu

include::./includes/attributes.adoc[]

The **OpenAPI Generator Moqu extension** converts an OpenAPI specification into a mock representation. This mock can then be mapped to the link:https://wiremock.org/[WireMock] for further use, providing a way to simulate APIs for testing and development purposes.

[NOTE]
====
Currently, this extension supports only link:https://wiremock.org/[WireMock] definitions.
====

[[getting-started]]
== Getting Started

[source,xml]
----
<dependency>
    <groupId>io.quarkiverse.openapi.generator</groupId>
    <artifactId>quarkus-openapi-generator-moqu-wiremock</artifactId>
    <version>{project-version}</version>
</dependency>
----

Now, create the following OpenAPI specification file under your `src/resources/openapi` directory:

[source,yaml]
.src/main/resources/openapi/hello.yaml
----
openapi: 3.0.3
servers:
  - url: http://localhost:8888
info:
  version: 999-SNAPSHOT
  title: Get framework by ID
paths:
  "/frameworks/{id}":
    get:
      parameters:
        - name: id
          in: path
          examples:
            quarkus:
              value: 1
      responses:
        200:
          content:
            "application/json":
              examples:
                quarkus:
                  $ref: "#/components/schemas/Framework"
          description: Ok
components:
  schemas:
    Framework:
      type: object
      properties:
        name:
          type: string
          example: "Quarkus"
        versions:
          type: array
          example: ["999-SNAPSHOT", "3.15.1"]
        supportsJava:
          type: boolean
          example: true
        contributors:
          type: integer
          example: 1000
        rules:
          type: object
          example:
            hello: world
----

Execute now your application on Dev mode, and access the Dev UI for getting you wiremock stubbing:

image::moqu-devui-card-framework.png[alt=Moque Dev UI card,width=640,height=480]

Click on `Moqu Wiremock`, you will se a table containing all wiremock definitions:

image::table-wiremock.png[alt=Wiremock mappings table,width=640,height=480]

Now, you can `see` or `download` the Wiremock stubbing.

== Serving mocks live with WireMock (Dev mode & Tests)

Add the link:https://docs.quarkiverse.io/quarkus-wiremock/dev/index.html[Quarkiverse WireMock] extension to your project:

[source,xml]
----
<dependency>
    <groupId>io.quarkiverse.wiremock</groupId>
    <artifactId>quarkus-wiremock</artifactId>
    <version>1.7.0</version>
</dependency>
----

With both dependencies present, `quarkus-wiremock` runs an embedded WireMock server as a Dev Service in both Dev mode and `@QuarkusTest`/`@QuarkusIntegrationTest` runs,
pre-loaded with your generated mocks.

Every time your project is built for Dev mode or tests, Moqu writes each request/response pair as an individual WireMock stub file. It picks the target directory in this order: `quarkus.openapi-generator.moqu.wiremock.output-dir`, if set; otherwise `quarkus.wiremock.devservices.files-mapping`, if customized away from its own default (`src/test/resources`) and not a `classpath:` location (see the note below); otherwise `target/moqu-wiremock`. So if you already point `files-mapping` somewhere of your own choosing, Moqu follows it automatically — no extra configuration needed:

[source,properties]
.src/main/resources/application.properties
----
quarkus.wiremock.devservices.files-mapping=target/moqu-wiremock
----

Whichever directory is chosen might already hold files you maintain by hand (most likely when it resolves to `files-mapping`'s own default, `src/test/resources`), so Moqu only deletes files it previously generated itself there, recognized by their `moqu-` filename prefix — everything else is left untouched.

NOTE: `classpath:`-prefixed `files-mapping` locations are never auto-followed, since the WireMock Dev Service reads that directory before Quarkus flushes generated resources onto the classpath. Point `files-mapping` (or `moqu.wiremock.output-dir`) at a plain filesystem path instead.

Running `mvn quarkus:dev` starts a real WireMock server pre-loaded with your generated mocks; the Dev UI's "WireMock" card links to its live mappings. Editing the OpenAPI spec regenerates the stubs and restarts WireMock with them (`quarkus.wiremock.devservices.reload` defaults to `true`).

The same wiring applies to `@QuarkusTest`. Use link:https://docs.quarkiverse.io/quarkus-wiremock/dev/index.html[`@ConnectWireMock`] to get the running server's URL injected, or to point a `@RestClient` straight at it:

[source,java]
----
@QuarkusTest
@ConnectWireMock
class FrameworkClientTest {

    WireMock wiremock; // <1>

    @Test
    void getsFrameworkFromMock() {
        // call your application code; it talks to WireMock, not a real backend
    }
}
----
<1> Injected automatically once `@ConnectWireMock` is present; use `restClient = "..."` on the annotation to redirect a specific REST client to the mock server for the test.

NOTE: Like the WireMock Dev Service itself, these generated stubs only exist for Dev mode and test builds — nothing is written, and nothing ships, in a production (`NORMAL`) build.

== Request matching

The Moqu extension uses the request and response examples defined in the OpenAPI Specification to determine the appropriate response for a specific request, creating a corresponding request/response pair.

Example:

[source,yaml]
----
openapi: 3.0.3
info:
  title: "Users API"
  version: 1.0.0-alpha
servers:
  - url: http://localhost:8888
paths:
  /users/{id}:
    get:
      description: Get user by ID
      parameters:
        - name: id
          in: path
          required: true
          schema:
            type: number
          examples:
            john: <1>
              value: 1 <2>
      responses:
        "200":
          description: Ok
          content:
            "application/json":
              examples:
                john: <3>
                  value:
                    '{"id": 1, "name": "John Doe"}'
----

<1> Defines an example named `john` for request
<2> Maps the request for path `/users/1` should use the response named as `john`
<3> Defines an example named `john` for response


In other words, if the user accesses `/users/1`, the response will be the one mapped for the `john` example in response.

The Wiremock definition using the OpenAPI specification above, looks something like this:

[source,json]
----
{
  "mappings": [
        {
          "request": {
          "method": "GET",
          "url": "/users/1"
        },
          "response": {
          "status": 200,
          "body": "{\"name\":\"John\",\"age\": 80}",
          "headers": {}
        }
      }
  ]
}
----

=== Response as Schema

You can use the `$ref` to reference a schema for mapping a response:

[source,yaml]
----
paths:
  "/users/{id}":
    get:
      parameters:
        - name: id
          in: path
          examples:
            alice:
              value: 1
      responses:
        200:
          content:
            "application/json":
              examples:
                alice:
                  $ref: "#/components/schemas/User"
          description: Ok
components:
  schemas:
    User:
      type: object
      properties:
        name:
          type: string
          example: "Alice"
        age:
          type: number
          example: 80
----

The Wiremock definition using the OpenAPI specification above, looks something like this:

[source,json]
----
{
    "mappings": [
        {
            "request": {
                "method": "GET",
                "url": "/users/1"
            },
            "response": {
                "status": 200,
                "body": "{\"name\":\"Alice\",\"age\":80}",
                "headers": {}
            }
        }
    ]
}
----
